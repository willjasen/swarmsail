# Swarmsail-managed Caddy ingress for Headscale

## Objective and initial state

Make Swarmsail generate and run Caddy alongside its managed Headscale instances. The local Headscale listener is private on Docker port 8080; Caddy owns LAN TCP 80/443, obtains and renews TLS with Cloudflare DNS-01, and routes each managed `server_url` hostname to its matching Headscale container. When enabled, the CrowdSec Caddy bouncer blocks active decisions and CrowdSec ingests Caddy JSON access logs. UDP 3478 remains disabled because embedded DERP is disabled.

Before the handoff, NPM Plus owned LAN port 80, Headscale directly owned LAN port 443 and terminated TLS, and Swarmsail generated only the Headscale service. The local DNS-only A record for `headscale.example.test` points to the MacBook LAN IP. The existing node-local Cloudflare token is mode 600 and is mounted read-only into Caddy; neither the token nor private key is stored in Git.

## Implementation

- Added a pinned Caddy image build with the Cloudflare DNS provider module.
- Extended `manage_headscale.py` so `caddy.enabled` generates a Caddy service and a node-local Caddyfile from each managed Headscale HTTPS origin. Caddy references the mounted token file, joins the Headscale network, binds only the configured LAN IP, and uses persistent node-local data/config directories.
- Added validation to prevent duplicate hostnames, direct public Headscale listeners, invalid HTTPS origins, and simultaneous NPM/Caddy ingress ownership.
- Added the pinned CrowdSec Caddy HTTP bouncer module. CrowdSec API keys are provided through a node-local Compose secret, never embedded in the generated Caddyfile or Compose environment. The Caddy default logger is limited to errors because the bouncer logs its configured key at info level; per-site JSON access logging remains enabled. Caddy writes those access logs to a shared node-local directory, and managed CrowdSec acquires them with the `crowdsecurity/caddy` collection.
- Placed NPM behind its opt-in `npm` Compose profile so it can be retained for rollback without claiming default ingress ports.

## Deployment and verification

Back up node-local `instances.json`, Headscale config, generated Compose, Swarmsail SQLite, and Headscale SQLite state before changing the live stack. Set `caddy.enabled: true`, configure its LAN bind IP, node-local config/data/state/log paths, and Cloudflare token file path. To enable the bouncer and log ingestion, set `crowdsec.enabled: true`, `crowdsec.timezone`, `crowdsec.required_for_public_hosts: true`, and `crowdsec.bouncer_api_key_path` to a node-local file containing the key generated by `docker compose -p <project> -f <crowdsec-compose.yml> exec crowdsec cscli bouncers add caddy-bouncer`. Keep the key file private and readable by the Caddy container user; do not put the key itself in `instances.json`. Caddy uses `http://crowdsec:8080` on the private Compose network unless `crowdsec.api_url` is set. Generate with `python3 manage_headscale.py generate --config <instances.json> --output <generated-compose.yml> --apply`; review the generated Caddyfile, acquisition file, and Compose before deployment.

The generated Caddyfile applies the bouncer and access log to every managed Headscale and configured proxy route. Managed CrowdSec installs the `crowdsecurity/caddy` collection and reads `/var/log/caddy/*.log` through a read-only bind mount. The generator pre-creates the configured `access.log` before Compose starts CrowdSec so acquisition can attach on its first startup; the Caddy container must be able to write to that directory. When using `docker-compose.orbstack.yml`, set `caddy.log_dir` to `$SWARMSAIL_LOCAL_DATA_DIR/caddy/logs`; its CrowdSec service is already configured to consume that same directory.

The Headscale config behind Caddy must keep `server_url` on HTTPS and use an internal `listen_addr` with empty TLS certificate/key paths. Deploy the generated service in the same Compose project and Docker network as the local control plane. Stop NPM Plus before binding Caddy to ports 80/443.

On 2026-10-18, the local service was deployed using Caddy 2.11.7 and `caddy-dns/cloudflare` 0.2.4. Headscale was recreated without a published host port and with TLS disabled internally. Caddy owns LAN TCP 80/443; NPM Plus is stopped but its node-local data remains. The Cloudflare token is mounted read-only from its node-local mode-600 file. ACME DNS-01 authorization succeeded and Caddy obtained a trusted certificate for `headscale.example.test`.

Verification passed for Swarmsail generator and Compose validation, `headscale configtest`, `caddy validate`, and requests to the Headscale health endpoint through Caddy. CrowdSec integration was subsequently verified in the isolated OrbStack test stack: CrowdSec parsed Caddy access logs, and a temporary decision changed a test client's response from HTTP 200 to HTTP 403. The decision was removed after verification. No existing node Tailscale identity was changed.

## Recovery and next phase

Rollback by disabling CrowdSec in `instances.json` and regenerating the Caddyfile/Compose to remove the bouncer and log mount; then, if restoring the old ingress, stop Caddy, restore the saved Headscale TLS config, and recreate Headscale with the TLS override before starting retained NPM with `--profile npm`. Keep Caddy certificate data, CrowdSec data, the bouncer key, and the old NPM volume unless the operator explicitly asks to remove them. Do not expose reusable enrollment keys or the CrowdSec bouncer key in Compose or logs. The bouncer protects HTTP(S) only; STUN remains direct UDP and is not covered.
